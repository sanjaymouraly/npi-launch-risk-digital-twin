# Contributing

Thanks for considering a contribution. This repository is a research-grade
reference implementation; the bar is *reproducible and honest* results, not volume.

## Development setup

```bash
git clone <your-fork> && cd npi-risk-digital-twin-ai
python3 -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt
cp .env.example .env
cd frontend && npm install && cd ..
```

## Before you open a pull request

```bash
pytest                          # backend: 118 tests, must be green
ruff check backend/app backend/tests scripts
cd frontend && npm run build    # tsc --noEmit && vite build
```

The CI workflow runs exactly these commands plus a migration smoke test and Docker
image builds.

## Principles this codebase follows

1. **No fabricated results.** Every number in the UI, the docs and the screenshots
   must come from a run. If a figure cannot be reproduced from a seed, it does not
   belong in the repository.
2. **Never blend the CPM and the constrained schedule.** They answer different
   questions and are always reported separately.
3. **State the uncertainty.** Iteration count, seed, convergence and percentile
   method travel with every probability.
4. **No hard-coded intervention benefits.** An intervention mutates the model; the
   benefit is measured.
5. **Say "insufficient data" rather than inventing a statistic.**
6. **Reproducible randomness.** Entity-keyed random streams; the same seed must
   reproduce a run.
7. **No secrets in the repository.** Use `.env` (git-ignored) or the provider
   settings screen; credentials are encrypted at rest and redacted from logs.

## Code layout

| Area | Location | Notes |
|---|---|---|
| Pure engines | `backend/app/{scheduling,simulation,optimization}` | No database access; operate on frozen dataclasses |
| Services | `backend/app/services` | Orchestration, persistence, audit |
| API | `backend/app/api` | Thin routers; business logic lives in services |
| AI | `backend/app/ai` | Providers, read-only tools, assistant |
| Frontend | `frontend/src` | React + TypeScript strict; no CSS framework |
| Tests | `backend/tests` | pytest + Hypothesis |
| Tooling | `scripts/` | Dataset build, demo bootstrap, benchmark, screenshots |

## Adding an intervention type

1. Implement it in `backend/app/optimization/interventions.py` as a **real mutation**
   of the planning model (durations, capacity, precedence, suppliers, materials,
   risks). Never add an expected-benefit constant.
2. Add it to `SUPPORTED_INTERVENTIONS` and, if needed, to the catalog generator.
3. Add a test in `backend/tests/test_optimization.py` asserting that the mutation
   changes the model.
4. Mention it in `docs/research/validation_report.md` if it changes the economics.

## Adding a page

1. Add the route in `frontend/src/App.tsx` and the navigation entry in
   `frontend/src/components/Layout.tsx`.
2. Use the existing design system in `frontend/src/components/ui.tsx`; add CSS to
   `frontend/src/styles.css` (no CSS framework, no inline style objects).
3. Fetch through `frontend/src/api.ts`; never call `fetch` directly in a component.

## Data

The programs in `data/samples/` are synthetic and generated by
`scripts/build_datasets.py`. If you change the generator, regenerate the samples and
re-run `python scripts/bootstrap_demo.py`, then refresh the screenshots with
`python scripts/capture_screenshots.py` — documentation must not show stale numbers.

## Commit messages

Short, imperative, and scoped, e.g. `engine(sgs): respect material release dates`.
Reference the issue or the research question when one exists.
